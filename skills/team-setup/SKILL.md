---
name: team-setup
description: Use when the user asks to set up, check, repair or update the Dream Team installation in the current repository. One pass, no arguments — it repairs what is local, asks one question at most (which missing plugins to install), pulls a clone-in-place team when it is behind, and reports what it did. Safe to run repeatedly. Never auto-invoke.
disable-model-invocation: true
user-invocable: true
---

You are the Team Setup. One pass, no modes: everything that is machine-local and reversible is checked and repaired without asking, the one thing that is not (installing a plugin) is asked once, and the report says what was done — never what would be done. Anything typed after the command is ignored.

## Steps

0. **Record.** Read `setup.record` from `.claude/team-manifest.json` (a file under the run-state directory, one `key=value` per line). Remember its `lastVersion` (absent → `none`) and `lastRun`. Nothing is written here; the record is written last, in step 12.
1. **Legacy run state.** Read `tracking` from the manifest. If the directory `tracking.legacyDir` exists at the project root, this project's run state is still in the legacy location and must move before any step reads or writes `tracking.dir`: run `bash .claude/{tracking.migration} --dry-run`. A clean dry run → run `bash .claude/{tracking.migration}` and report its output verbatim, including the project files it lists for the user to edit by hand. A refused or failed dry run (a run is open, or names exist in both directories) → report its message and instruction verbatim and continue in **legacy mode**: steps 5, 10 and 12 write nothing under `tracking.dir`, step 1b is skipped, step 6 writes nothing under `knowledge.operativeDir` (which lies inside it), step 7 does not look at the learnings inbox, and the report says `legacy {tracking.legacyDir} present: {reason}`. Never move, copy or delete run-state files yourself.
1b. **Knowledge layout.** Runs after step 5, not here: the migration refuses while a run's marker is open, and step 5 is what deletes a stale one. It still runs before step 6, which writes into the directory the migration moves files to. Skipped in legacy mode (the report says `not checked (legacy mode)`). Otherwise run `bash .claude/{knowledge.migration} --dry-run` from the project root. A clean dry run (exit 0) → run `bash .claude/{knowledge.migration}` and report what it prints verbatim: the two `operative: …` lines, the `project: …` line, and a `note: …` line when it prints one. The second `operative:` line says where the learnings inbox now lives: `operative: <profile directory> (key <project key>): …` when it is in the developer's profile, which every working copy of the repository on this machine shares, or `operative: per-copy <dir> (<reason>)` when it stays in this working copy (no remote to derive the key from, the profile disabled in the manifest, the profile not writable, or an older `LEARNINGS.md` the migration cannot split, whose fix the reason names). Exit 1 (refused: a run is open, a name exists on both sides, or a precondition does not hold) → report its message verbatim and continue; exit 2 → report it as `not checked` with the script's message and continue. Two states of the project files are reported with the command the lead runs, because setup never runs `--first-commit` or `--drop-legacy` itself. When the `project:` line says it is waiting for `knowledge.dir` in the repository, add the lead's order: `bash .claude/{knowledge.migration} --first-commit`, then `/generate-knowledge` (it takes the machine section out of `TOOLCHAIN.md` and team paths out of the text), then a commit of `knowledge.dir` alone, one commit and one pull request. When the `project:` line starts `project: in place` and `knowledge.legacyDir` still exists at the project root (the script says "private copy kept" only on the run that imports, so check the directory, not the wording), add that `bash .claude/{knowledge.migration} --drop-legacy` removes the private copy once the lead is ready for it. The migration is **pending** when its real run did not exit 0 or was not run (a refused dry run, exit 2, legacy mode) and `bash .claude/{knowledge.resolver} operative` prints `knowledge.legacyDir`: step 6 then writes nothing under `knowledge.operativeDir`, because a file there makes the resolver point every reader at a new, empty inbox while the real one waits in the legacy directory, and every later migration refuses on the names that now exist on both sides. Never move, copy or delete knowledge files yourself.
2. **Team files.** The team is deployed as one layer: the repository's contents sit directly in `.claude/`, which is where Claude Code discovers agents and skills, so there are no copies or links to keep in sync. For each name in `agents[]` verify `.claude/agents/<name>.md` exists and its frontmatter `name:` matches; for each in `skills[]` verify `.claude/skills/<name>/SKILL.md`. For the `team` skill also verify that `.claude/skills/team/references/` holds one file per workflow named in the marker block of the team skill (`analyze.md` … `full_feature.md`); a missing one is reported like a missing skill. Verify every template path under `templates` exists and that `templates.standards` and `templates.interface` each contain `_generic.md`. Verify too that every script the `checks` block names exists under `.claude/`, and so do `setup.normalizer`, `tracking.migration`, `knowledge.migration`, `knowledge.resolver`, `knowledge.learningsIndex` and `knowledge.inbox`: a deployment that lost them passes every other test in this skill while `/generate-knowledge` silently cannot verify its own work. Report anything missing by name; a missing file means an incomplete deployment, and the fix is `{update.pull}` for a clone or `{update.copy}` for a copy (step 9 says which this is), which this skill never runs for that reason by itself.
3. **Stack neutrality.** Run `checks.stackNeutralityLint` from the manifest via Bash, from the directory named in `checks.runFrom`. Expected: no output. Any hit is reported as a team defect (file:line).
4. **Version control.** Generated files are hidden in three places and all three are checked, two are repaired:
   - `.claude/.gitignore` ships with the team and covers `knowledge/`, `settings.json` and `settings.local.json` from inside `.claude/`; `knowledge/` now hides only the legacy private copy. Verify it exists and still carries those lines; if it was deleted or edited, report it — this skill never rewrites it. The committed knowledge directory is never hidden: this skill never writes `knowledge.dir` or its parent to `.git/info/exclude`.
   - `.git/info/exclude` is machine-local and needs no commit, so it comes first: for `{tracking.dir}/` and every entry in `gitExclude[]` that the project's `.gitignore` does not already hide, append the missing line. When `.claude/.git` exists (a clone in place, step 9), also `.claude/` itself: without that line a `git add .` in the project records the clone as a bare gitlink that gives a teammate an empty `.claude/`. Create `.git/info/` and the file when they are absent. Report every line written.
   - The project's `.gitignore` is committed and is the project's own: write to it only when it already carries a line for `tracking.legacyDir` — the project chose to commit its ignore, so keep that choice current by replacing the legacy line with `{tracking.dir}/`. Otherwise leave it alone; the report says so.
5. **Run state.** Run `bash .claude/{setup.normalizer}` from the project root and report how many first lines it normalized (`normalized …` lines), or `none to normalize`. Then the marker: if `hooks.marker` exists, read it and report the run it names. Its `status.md` missing → stale: delete the marker (`rm -f`, then `ls -a` to see it gone) and report it. Its first line closed (`[DONE` or `Complete —` anywhere) and the marker carrying `state=closed` → report `warm: {context_id} ({result})` and leave it: the run is collecting feedback. First line closed without `state=closed` → stale, same handling as missing. Otherwise report the open run with its phase. Then perform step 1b, and continue with step 6.
6. **Capabilities.** Read `plugins[]` and `pluginPolicy` from the manifest.
   - **Detect.** For each entry, decide whether its capability is actually present: check the tools and commands available in this session against the entry's `detect` description, and, if the `claude` command-line tool is reachable, cross-check `claude plugin list`. Report a capability as available only when you can see it, not because the plugin name appears in a list.
   - **Offer.** When at least one capability is missing: one AskUserQuestion, multi-select, one option per missing *capability* — the two `browser-control` entries are one option naming `chrome-devtools-mcp`, whose description names `playwright` as the alternative the user may prefer — each option saying what the capability lets the team do, plus the option "Install nothing now". Install the picked ones with each entry's `install` command, one after another, and report each result. Never install two entries that share a `capability`, never install anything the user did not pick in this run's question, never enable or disable a plugin. No question at all when nothing is missing.
   - **Write `CAPABILITIES.md`.** In legacy mode write nothing under `knowledge.operativeDir` and report `not written (legacy mode)`. While the knowledge migration is pending (step 1b), write nothing there either and report `not written (knowledge migration pending)`. Otherwise render `templates.capabilities` into `knowledge.environment.CAPABILITIES.md` under `knowledge.capabilitiesDir`: available capabilities with their brokering and roles, unavailable ones with their install commands, and the `useWhen` / `neverUseFor` rules copied verbatim from the manifest for the available ones only. If nothing is available, still write the file with "None detected." — the agents read it either way. Rewrite the file completely on every run; it describes the machine, not the repository, so it is never merged or hand-edited.
   - **Direct access.** For each available capability whose `usedBy` names a subagent, report that the role would need the capability's tools added to its frontmatter to call it directly, and that by default the orchestrator brokers it. Report only; never edit an agent.
7. **Knowledge.** Find the project directory with `bash .claude/{knowledge.resolver} project` and check that each file in `knowledge.required` is present in it. If required files are missing, the report says to run `knowledge.generator`. Then the learnings inbox: run `bash .claude/{knowledge.inbox} where` and report its lines on the `Learnings inbox:` line: the second says where the inbox lives (`profile (key <key>)`, `per-copy (<reason>)`, or `legacy (…)` while the knowledge migration is pending), the first is its directory, and a third, when there is one, is a note. Exit 2 → report `not checked` with its message and continue. In legacy mode skip it and report `not checked (legacy mode)`. This step creates nothing: an inbox without a `learnings/` directory is the correct state of a project that has not produced an entry yet, and the inbox tool creates it with the first entry. Then run `checks.knowledgeScaffold` as `checks.knowledgeScaffoldRunFrom` spells out: exit 3 means the knowledge files are scaffolds written on an empty project (the date is on its second line) and the report says so with `/generate-knowledge` due once the code exists; exit 1 means those scaffolds now sit on a project that has content, and the report says to run `/generate-knowledge`. Exit 0 adds nothing; exit 2 is reported as `not checked` with the script's message.
8. **Hooks.** Read the `hooks` block of the manifest and make sure the team can keep a run active across model switches and restarts, hear feedback after a run closes, and deny destructive shell commands during a run:
   - Files: `hooks.launcher` and every script it dispatches exist under `hooks.dir`.
   - Wiring: read the project's `.claude/settings.json`; create it as `{}` when absent. For each entry of `hooks.settingsSnippet` — the `UserPromptSubmit` entry whose command names `run-hook.cmd team-mode-prompt`, and the `PreToolUse` entry, with its `matcher`, whose command names `run-hook.cmd guard-command` — that the file lacks, append it to its array, creating the array when absent; never replace an existing hooks block. When an entry exists but its `command` differs from the snippet's (stale wiring, left by an older team), replace that string and nothing else in the entry. Report `wired`, `rewired` or `already wired` per entry, and that a newly added or changed hook is picked up after the user opens `/hooks` once or restarts the session. The command is a plain project-relative path on purpose: other harnesses read the same file and run it without bash.
   - Shell: a bash interpreter must be reachable, otherwise the hooks exit quietly: sticky mode is unavailable and the guard denies nothing. Report `bash: found|absent (sticky mode and guard disabled)`.
9. **Update.** Read `update` from the manifest. If `.claude/.git` exists, this is a clone in place: run `git -C .claude remote update` — the only network access this skill makes, against the remote the user cloned from. A failure there → report `could not reach the remote`, skip the pull and continue at step 10. Then `git -C .claude status --porcelain` and `git -C .claude rev-list --count HEAD..@{u}`. The count fails (a detached HEAD, a tag, a branch without an upstream) → report `not on a branch with an upstream; {update.pull} by hand` and continue at step 10. Behind by N > 0 with a clean working tree → run `{update.pull}`. The pull fails (local commits in the clone, so no fast-forward) → report git's message and `{update.pull}`, change nothing, continue at step 10. The pull succeeds → read `team.version` from the pulled manifest, report `pulled {old} → {new}: reopen the session and run /team-setup again`, write the record (step 12) **with `lastVersion={old}`** — the version whose prompts ran this pass; the next pass compares it with the new `team.version` and performs the steps in between — and **stop here**: the new prompts are not loaded in this session, and the steps below would run the old ones. Behind with a dirty working tree → report the files and `{update.pull}`, do not pull. Behind by 0 → `up to date`. If `.claude/.git` does not exist, this is a copy: report `copy install; update with {update.copy}` and run no git command there.
10. **Post-update steps.** When `lastVersion` differs from `team.version` (a `none` record counts as every version): for every key of `setup.postUpdate` greater than `lastVersion` (all of them for `none`), oldest first, perform its `do` step yourself — step 5 already ran the normalizer, so the `4.5.0` step is reported as done; the `5.0.0` step counts as done only when step 1b's real run exited 0, otherwise it is reported as pending with step 1b's message (the record may still advance: 1b runs again on every pass) — and collect its `knowledge` steps into one report line: `Knowledge: /generate-knowledge is due ({lastVersion} → {team.version}: {the steps, comma-separated})`. Skip the `knowledge` steps when the record is `none` and no `knowledge.required` file exists yet: a fresh install has nothing to regenerate, and step 7 already names the generator. The generator is a command only the user starts; this skill names it once and never runs it. Then read `amendments.file` from the manifest, when it exists. Count its entries, the `## ` headings below the header. If its `Team version checked:` line differs from `team.version`, report `Team amendments: N to re-check at the next /team run`; otherwise `N active`. The re-check is `/team`'s; change nothing in the file.
11. **Toolchain.** If `knowledge.toolchainMissingFile` exists, read it and report it verbatim.
12. **Record.** Write `setup.record` whole, with Write: `lastVersion={team.version}`, `lastRun={YYYY-MM-DD}`, `install={clone | copy}`. In legacy mode skip it and say so.

## Rules

- Never modify agents, skills, or templates. The only knowledge file you may write is `CAPABILITIES.md` in `knowledge.capabilitiesDir`, neither in legacy mode nor while the knowledge migration is pending (step 1b). The migration script moves files into `knowledge.operativeDir`, `knowledge.capabilitiesDir` and the developer's profile and nowhere else. Never write in `knowledge.dir`, and never in the learnings inbox: runs fill it through `{knowledge.inbox}`.
- Nothing outside the project is reached except through the team's tools: the resolver, the knowledge migration and the inbox tool find and write the developer's profile; this skill never reads or writes a path there with a file tool, and no step asks for access to it.
- Never install, enable or disable a plugin the user did not pick in this run's one question.
- Never edit the team's `.claude/.gitignore`. Edit the project's own `.gitignore` only as step 4 describes: the legacy run-state line, replaced by the current one.
- Never run any command other than the manifest lint, `claude plugin list` and the `install` command of a picked plugin, a bash availability check, the run-state migration script and its dry run, the knowledge migration script and its dry run (never with `--first-commit` or `--drop-legacy`), the knowledge resolver, the inbox tool's `where`, the normalizer, the scaffold check, `git -C .claude remote update`, `git -C .claude status --porcelain`, `git -C .claude rev-list --count HEAD..@{u}`, `{update.pull}`, `rm -f` of a stale marker, and reading files.
- The files this pass may change, each reported by name: `.git/info/exclude`, the legacy run-state line of the project's `.gitignore`, the run state the migration moves (and the knowledge it rewrites), the operative files the knowledge migration moves into `knowledge.operativeDir` and `knowledge.capabilitiesDir` and the inbox it moves into the developer's profile (with the inbox entries, the backup and the stamp it writes), the first lines the normalizer rewrites, a stale marker, `.claude/settings.json` (the two hook entries only), `CAPABILITIES.md`, `setup.record`, the team's own clone when it is pulled, and the plugins the user picked.
- Never copy, move or delete a team file. A missing or edited agent, skill or template is reported and left alone; replacing the deployment is the user's call, with the command the report shows.
