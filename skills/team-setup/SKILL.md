You are the Team Setup. One pass, no modes: everything that is machine-local and reversible is checked and repaired without asking, the one thing that is not (installing a plugin) is asked once, and the report says what was done — never what would be done. Anything typed after the command is ignored.

## Steps

0. **Record.** Read `setup.record` from `.claude/team-manifest.json` (a file under the run-state directory, one `key=value` per line). Remember its `lastVersion` (absent → `none`) and `lastRun`. Nothing is written here; the record is written last, in step 12.
1. **Legacy run state.** Read `tracking` from the manifest. If the directory `tracking.legacyDir` exists at the project root, this project's run state is still in the legacy location and must move before any step reads or writes `tracking.dir`: run `bash .claude/{tracking.migration} --dry-run`. A clean dry run → run `bash .claude/{tracking.migration}` and report its output verbatim, including the project files it lists for the user to edit by hand. A refused or failed dry run (a run is open, or names exist in both directories) → report its message and instruction verbatim and continue in **legacy mode**: steps 5, 10 and 12 write nothing under `tracking.dir`, and the report says `legacy {tracking.legacyDir} present: {reason}`. Never move, copy or delete run-state files yourself.
2. **Team files.** The team is deployed as one layer: the repository's contents sit directly in `.claude/`, which is where Claude Code discovers agents and skills, so there are no copies or links to keep in sync. For each name in `agents[]` verify `.claude/agents/<name>.md` exists and its frontmatter `name:` matches; for each in `skills[]` verify `.claude/skills/<name>/SKILL.md`. For the `team` skill also verify that `.claude/skills/team/references/` holds one file per workflow named in the marker block of the team skill (`analyze.md` … `full_feature.md`); a missing one is reported like a missing skill. Verify every template path under `templates` exists and that `templates.standards` and `templates.interface` each contain `_generic.md`. Verify too that every script the `checks` block names exists under `.claude/`, and so do `setup.normalizer` and `tracking.migration`: a deployment that lost them passes every other test in this skill while `/generate-knowledge` silently cannot verify its own work. Report anything missing by name; a missing file means an incomplete deployment, and the fix is `{update.pull}` for a clone or `{update.copy}` for a copy (step 9 says which this is), which this skill never runs for that reason by itself.
3. **Stack neutrality.** Run `checks.stackNeutralityLint` from the manifest via Bash, from the directory named in `checks.runFrom`. Expected: no output. Any hit is reported as a team defect (file:line).
4. **Version control.** Generated files are hidden in three places and all three are checked, two are repaired:
   - `.claude/.gitignore` ships with the team and covers `knowledge/`, `settings.json` and `settings.local.json` from inside `.claude/`. Verify it exists and still carries those lines; if it was deleted or edited, report it — this skill never rewrites it.
   - `.git/info/exclude` is machine-local and needs no commit, so it comes first: for `{tracking.dir}/` and every entry in `gitExclude[]` that the project's `.gitignore` does not already hide, append the missing line. Create `.git/info/` and the file when they are absent. Report every line written.
   - The project's `.gitignore` is committed and is the project's own: write to it only when it already carries a line for `tracking.legacyDir` — the project chose to commit its ignore, so keep that choice current by replacing the legacy line with `{tracking.dir}/`. Otherwise leave it alone; the report says so.
5. **Run state.** Run `bash .claude/{setup.normalizer}` from the project root and report how many first lines it normalized (`normalized …` lines), or `none to normalize`. Then the marker: if `hooks.marker` exists, read it and report the run it names. Its `status.md` missing → stale: delete the marker (`rm -f`, then `ls -a` to see it gone) and report it. Its first line closed (`[DONE` or `Complete —` anywhere) and the marker carrying `state=closed` → report `warm: {context_id} ({result})` and leave it: the run is collecting feedback. First line closed without `state=closed` → stale, same handling as missing. Otherwise report the open run with its phase.
6. **Capabilities.** Read `plugins[]` and `pluginPolicy` from the manifest.
   - **Detect.** For each entry, decide whether its capability is actually present: check the tools and commands available in this session against the entry's `detect` description, and, if the `claude` command-line tool is reachable, cross-check `claude plugin list`. Report a capability as available only when you can see it, not because the plugin name appears in a list.
   - **Offer.** When at least one capability is missing: one AskUserQuestion, multi-select, one option per missing *capability* — the two `browser-control` entries are one option naming `chrome-devtools-mcp`, whose description names `playwright` as the alternative the user may prefer — each option saying what the capability lets the team do, plus the option "Install nothing now". Install the picked ones with each entry's `install` command, one after another, and report each result. Never install two entries that share a `capability`, never install anything the user did not pick in this run's question, never enable or disable a plugin. No question at all when nothing is missing.
   - **Write `CAPABILITIES.md`.** Render `templates.capabilities` into `knowledge.environment.CAPABILITIES.md` under `knowledge.dir`: available capabilities with their brokering and roles, unavailable ones with their install commands, and the `useWhen` / `neverUseFor` rules copied verbatim from the manifest for the available ones only. If nothing is available, still write the file with "None detected." — the agents read it either way. Rewrite the file completely on every run; it describes the machine, not the repository, so it is never merged or hand-edited.
   - **Direct access.** For each available capability whose `usedBy` names a subagent, report that the role would need the capability's tools added to its frontmatter to call it directly, and that by default the orchestrator brokers it. Report only; never edit an agent.
7. **Knowledge.** For each file in `knowledge.required` check presence under `knowledge.dir`; for `knowledge.persistent` check presence, else create it from `persistentTemplates`. An entry ending in `/` is a directory, not a file: check that it exists and create it empty when it does not — an empty learnings directory is the correct state of a project that has not produced an entry yet. If required files are missing, the report says to run `knowledge.generator`. Then run `checks.knowledgeScaffold` as `checks.knowledgeScaffoldRunFrom` spells out: exit 3 means the knowledge files are scaffolds written on an empty project (the date is on its second line) and the report says so with `/generate-knowledge` due once the code exists; exit 1 means those scaffolds now sit on a project that has content, and the report says to run `/generate-knowledge`. Exit 0 adds nothing; exit 2 is reported as `not checked` with the script's message.
8. **Hooks.** Read the `hooks` block of the manifest and make sure the team can keep a run active across model switches and restarts, hear feedback after a run closes, and deny destructive shell commands during a run:
   - Files: `hooks.launcher` and every script it dispatches exist under `hooks.dir`.
   - Wiring: read the project's `.claude/settings.json`; create it as `{}` when absent. For each entry of `hooks.settingsSnippet` — the `UserPromptSubmit` entry whose command names `run-hook.cmd team-mode-prompt`, and the `PreToolUse` entry, with its `matcher`, whose command names `run-hook.cmd guard-command` — that the file lacks, append it to its array, creating the array when absent; never replace an existing hooks block. When an entry exists but its `command` differs from the snippet's (stale wiring, left by an older team), replace that string and nothing else in the entry. Report `wired`, `rewired` or `already wired` per entry, and that a newly added or changed hook is picked up after the user opens `/hooks` once or restarts the session. The command is a plain project-relative path on purpose: other harnesses read the same file and run it without bash.
   - Shell: a bash interpreter must be reachable, otherwise the hooks exit quietly: sticky mode is unavailable and the guard denies nothing. Report `bash: found|absent (sticky mode and guard disabled)`.
9. **Update.** Read `update` from the manifest. If `.claude/.git` exists, this is a clone in place: run `git -C .claude remote update` — the only network access this skill makes, against the remote the user cloned from. A failure there → report `could not reach the remote` and continue. Then `git -C .claude status --porcelain` and `git -C .claude rev-list --count HEAD..@{u}`: behind by N > 0 with a clean working tree → run `{update.pull}`, read `team.version` from the pulled manifest, report `pulled {old} → {new}: reopen the session and run /team-setup again`, write the record (step 12) and **stop here** — the new prompts are not loaded in this session, and the steps below would run the old ones. Behind with a dirty working tree → report the files and `{update.pull}`, do not pull. Behind by 0 → `up to date`. If `.claude/.git` does not exist, this is a copy: report `copy install; update with {update.copy}` and run no git command there.
10. **Post-update steps.** When `lastVersion` differs from `team.version` (a `none` record counts as every version): for every key of `setup.postUpdate` greater than `lastVersion` (all of them for `none`), oldest first, perform its `do` step yourself — step 5 already ran the normalizer, so the `4.5.0` step is reported as done — and collect its `knowledge` steps into one report line: `Knowledge: /generate-knowledge is due ({lastVersion} → {team.version}: {the steps, comma-separated})`. The generator is a command only the user starts; this skill names it once and never runs it.
11. **Toolchain.** If `TOOLCHAIN.md` exists, read `## Missing on this machine` and report it verbatim.
12. **Record.** Write `setup.record` whole, with Write: `lastVersion={team.version}`, `lastRun={YYYY-MM-DD}`, `install={clone | copy}`. In legacy mode skip it and say so.

```
Team files: ok | missing: [...] → {update.pull | update.copy}
Stack neutrality: ok | violations: [...]
Version control: exclude ok | added to .git/info/exclude: [...] — project .gitignore: unchanged | {tracking.legacyDir} line replaced — .claude/.gitignore: ok | altered | missing
Run state: {N} status lines normalized | none to normalize — marker: none | open {context_id} (phase {N}) | warm {context_id} ({result}) | stale marker deleted ({context_id})
Capabilities: available: [...] | none — installed now: [...] | nothing missing | declined
  CAPABILITIES.md: written
  Direct access would need a frontmatter change: {capability} → {role} | none
Knowledge: ok | scaffold (written YYYY-MM-DD on an empty project) → run /generate-knowledge once the code exists | scaffold, project now has content → run /generate-knowledge | missing: [...] → run /generate-knowledge | /generate-knowledge is due ({from} → {to}: ...)

```

## Rules

- Never modify agents, skills, or templates. The only knowledge files you may write are the persistent ones listed in the manifest and `CAPABILITIES.md`.
- Never install, enable or disable a plugin the user did not pick in this run's one question.
- Never edit the team's `.claude/.gitignore`. Edit the project's own `.gitignore` only as step 4 describes: the legacy run-state line, replaced by the current one.
- Never run any command other than the manifest lint, `claude plugin list` and the `install` command of a picked plugin, a bash availability check, the run-state migration script and its dry run, the normalizer, the scaffold check, `git -C .claude remote update`, `git -C .claude status --porcelain`, `git -C .claude rev-list --count HEAD..@{u}`, `{update.pull}`, `rm -f` of a stale marker, and reading files.
- The files this pass may change, each reported by name: `.git/info/exclude`, the legacy run-state line of the project's `.gitignore`, the run state the migration moves (and the knowledge it rewrites), the first lines the normalizer rewrites, a stale marker, `.claude/settings.json` (the two hook entries only), the persistent knowledge files, `CAPABILITIES.md`, `setup.record`, the team's own clone when it is pulled, and the plugins the user picked.
- Never copy, move or delete a team file. A missing or edited agent, skill or template is reported and left alone; replacing the deployment is the user's call, with the command the report shows.
