**Team root.** `{team}` stands for the team root, the directory that holds `team-manifest.json`: `${CLAUDE_PLUGIN_ROOT}`. If that name reads as an unexpanded variable, the team root is the one given in your prompt. Double-quote a team path in a shell command. Under `.dream-team-tracking/` write `{team}/…` as it stands, never the resolved path.

You are the Team Setup. One pass, no modes: everything that is machine-local and reversible is checked and repaired without asking, the two things that are not (removing an old in-project install, installing a plugin) are each asked once, and the report says what was done — never what would be done. Anything typed after the command is ignored.

## Steps

0. **Record.** Read `setup.record` from `{team}/team-manifest.json` (a file under the run-state directory, one `key=value` per line). Remember its `lastVersion` (absent → `none`) and `lastRun`. Nothing is written here; the record is written last, in step 12.
1. **Legacy run state.** Read `tracking` from the manifest. If the directory `tracking.legacyDir` exists at the project root, this project's run state is still in the legacy location and must move before any step reads or writes `tracking.dir`: run `bash "{team}/{tracking.migration}" --dry-run`. A clean dry run → run `bash "{team}/{tracking.migration}"` and report its output verbatim, including the project files it lists for the user to edit by hand. A refused or failed dry run (a run is open, or names exist in both directories) → report its message and instruction verbatim and continue in **legacy mode**: steps 5, 10 and 12 write nothing under `tracking.dir`, and the report says `legacy {tracking.legacyDir} present: {reason}`. Never move, copy or delete run-state files yourself.
2. **Team files.** The team is a plugin: its files sit in the team root, which the plugin mechanism installs whole, so nothing is verified there. This step looks for an **old install**: the team cloned or copied into the project's `.claude/` by a version before 5.0.0. It shadows the plugin's commands and roles and keeps its own hooks wired, and it is present when `.claude/team-manifest.json` exists in the project. Absent → report `plugin` and continue.
   - **Refuse**, removing nothing and saying why, in two cases. A run is open (`hooks.marker` exists, does not carry `state=closed`, and its `status.md` is not closed): the report says to finish it or `/team stop` first. Or `.claude/.git` exists and `git -C .claude status --porcelain --untracked-files=no` prints anything: someone edited the old team in place, the report lists those files, and what becomes of the edits is the lead's call. The remaining steps still run.
   - **Ask** otherwise, once, with AskUserQuestion: remove the old install now, or leave it. Left → report `old install left in place` and continue. While it stays, the short command names run the old copy and the plugin's hooks stay silent in this project.
   - **Remove**, on yes, exactly this. A clone (`.claude/.git` exists): take the list from `git -C .claude ls-files`, delete each listed file, then each directory under `.claude/` that this left empty, then `.claude/.git`. A copy (no `.claude/.git`): read `agents[]` and `skills[]` from the old `.claude/team-manifest.json` first, then delete `.claude/agents/<name>.md` for each of those agents, `.claude/skills/<name>/` for each of those skills, the directories `.claude/templates/`, `.claude/hooks/`, `.claude/tools/`, `.claude/checks/`, `.claude/copilot/` and `.claude/.github/`, and the files `.claude/team-manifest.json`, `.claude/README.md`, `.claude/.gitignore` and `.claude/.gitattributes`. Then, in `.claude/settings.json`, remove the hook entries whose `command` names `.claude/hooks/run-hook.cmd`, with an array or a `hooks` block that this leaves empty, and nothing else in that file.
   - **Never touched**: `.claude/knowledge/`, `.claude/settings.local.json`, the rest of `.claude/settings.json`, `.claude/PROJECT.md`, `.claude/docs/`, and any file the old install did not ship.
   - Report every path removed, and that the session must be reopened before the next command: the old commands and roles stay loaded until then. Only a pass started as `/dream-team:team-setup` reaches this step while an old install is present; the short name runs the old copy.
3. **Stack neutrality.** Run `checks.stackNeutralityLint` from the manifest via Bash, from the directory named in `checks.runFrom`. Expected: no output. Any hit is reported as a team defect (file:line).
4. **Version control.** Generated files are hidden in two places; the first is repaired, the second only kept current:
   - `.git/info/exclude` is machine-local and needs no commit, so it comes first: for every entry in `gitExclude[]` that the project's `.gitignore` does not already hide, append the missing line. Create `.git/info/` and the file when they are absent. Report every line written. A `.claude/` line that an earlier setup wrote there is left in place and named in the report: it is machine-local, and removing it would surface files in a project that relied on it.
   - The project's `.gitignore` is committed and is the project's own: write to it only when it already carries a line for `tracking.legacyDir` — the project chose to commit its ignore, so keep that choice current by replacing the legacy line with `{tracking.dir}/`. Otherwise leave it alone; the report says so.
5. **Run state.** Run `bash "{team}/{setup.normalizer}"` from the project root and report how many first lines it normalized (`normalized …` lines), or `none to normalize`. Then the marker: if `hooks.marker` exists, read it and report the run it names. Its `status.md` missing → stale: delete the marker (`rm -f`, then `ls -a` to see it gone) and report it. Its first line closed (`[DONE` or `Complete —` anywhere) and the marker carrying `state=closed` → report `warm: {context_id} ({result})` and leave it: the run is collecting feedback. First line closed without `state=closed` → stale, same handling as missing. Otherwise report the open run with its phase.
6. **Capabilities.** Read `plugins[]` and `pluginPolicy` from the manifest.
   - **Detect.** For each entry, decide whether its capability is actually present: check the tools and commands available in this session against the entry's `detect` description, and, if the `claude` command-line tool is reachable, cross-check `claude plugin list`. Report a capability as available only when you can see it, not because the plugin name appears in a list.
   - **Offer.** When at least one capability is missing: one AskUserQuestion, multi-select, one option per missing *capability* — the two `browser-control` entries are one option naming `chrome-devtools-mcp`, whose description names `playwright` as the alternative the user may prefer — each option saying what the capability lets the team do, plus the option "Install nothing now". Install the picked ones with each entry's `install` command, one after another, and report each result. Never install two entries that share a `capability`, never install anything the user did not pick in this run's question, never enable or disable a plugin. No question at all when nothing is missing.
   - **Write `CAPABILITIES.md`.** Render `templates.capabilities` into `knowledge.environment.CAPABILITIES.md` under `knowledge.dir`: available capabilities with their brokering and roles, unavailable ones with their install commands, and the `useWhen` / `neverUseFor` rules copied verbatim from the manifest for the available ones only. If nothing is available, still write the file with "None detected." — the agents read it either way. Rewrite the file completely on every run; it describes the machine, not the repository, so it is never merged or hand-edited.
   - **Direct access.** For each available capability whose `usedBy` names a subagent, report that the role would need the capability's tools added to its frontmatter to call it directly, and that by default the orchestrator brokers it. Report only; never edit an agent.
7. **Knowledge.** For each file in `knowledge.required` check presence under `knowledge.dir`; for `knowledge.persistent` check presence, else create it from `persistentTemplates`. An entry ending in `/` is a directory, not a file: check that it exists and create it empty when it does not — an empty learnings directory is the correct state of a project that has not produced an entry yet. If required files are missing, the report says to run `knowledge.generator`. Then run `checks.knowledgeScaffold` as `checks.knowledgeScaffoldRunFrom` spells out: exit 3 means the knowledge files are scaffolds written on an empty project (the date is on its second line) and the report says so with `/generate-knowledge` due once the code exists; exit 1 means those scaffolds now sit on a project that has content, and the report says to run `/generate-knowledge`. Exit 0 adds nothing; exit 2 is reported as `not checked` with the script's message.
8. **Hooks.** The plugin registers its own hooks, described by the `hooks` block of the manifest: they keep a run active across model switches and restarts, hear feedback after a run closes, and deny destructive shell commands during a run. Nothing is wired in the project and this skill writes no hook entry anywhere.
   - Stale wiring: when no old install is present (step 2 found none, or removed it) and the project's `.claude/settings.json` still carries a hook entry whose `command` names `.claude/hooks/run-hook.cmd`, that entry points at a file that is gone and fails on every prompt. Remove it, with an array or a `hooks` block that this leaves empty, and nothing else in that file. Report `stale wiring removed` or `no stale wiring`.
   - Shell: a bash interpreter must be reachable, otherwise the hooks exit quietly: sticky mode is unavailable and the guard denies nothing. Report `bash: found|absent (sticky mode and guard disabled)`.
9. **Update.** The team is updated by the plugin mechanism, never by this skill, which contacts no network. Read `update` from the manifest and report the running version, `team.version`, with `update.command` as the way to update.
10. **Post-update steps.** When `lastVersion` differs from `team.version` (a `none` record counts as every version): for every key of `setup.postUpdate` greater than `lastVersion` (all of them for `none`), oldest first, perform its `do` step yourself — step 5 already ran the normalizer, so the `4.5.0` step is reported as done — and collect its `knowledge` steps into one report line: `Knowledge: /generate-knowledge is due ({lastVersion} → {team.version}: {the steps, comma-separated})`. Skip the `knowledge` steps when the record is `none` and no `knowledge.required` file exists yet: a fresh install has nothing to regenerate, and step 7 already names the generator. The generator is a command only the user starts; this skill names it once and never runs it. Then read `amendments.file` from the manifest, when it exists. Count its entries, the `## ` headings below the header. If its `Team version checked:` line differs from `team.version`, report `Team amendments: N to re-check at the next /team run`; otherwise `N active`. The re-check is `/team`'s; change nothing in the file.
11. **Toolchain.** If `TOOLCHAIN.md` exists, read `## Missing on this machine` and report it verbatim.
12. **Record.** Write `setup.record` whole, with Write: `lastVersion={team.version}`, `lastRun={YYYY-MM-DD}`, `install=plugin`. In legacy mode skip it and say so.

```
Tracking: ok | migrated this run ({N} entries) | legacy {tracking.legacyDir} present: {reason it was not moved}
Team files: plugin | old install removed: [...] — reopen the session | old install left in place | old install not removed: {reason}
Stack neutrality: ok | violations: [...]
Version control: exclude ok | added to .git/info/exclude: [...] — an earlier line hides .claude/ whole: left | none — project .gitignore: unchanged | {tracking.legacyDir} line replaced
Run state: {N} status lines normalized | none to normalize — marker: none | open {context_id} (phase {N}) | warm {context_id} ({result}) | stale marker deleted ({context_id})
Capabilities: available: [...] | none — installed now: [...] | nothing missing | declined
  CAPABILITIES.md: written
  Direct access would need a frontmatter change: {capability} → {role} | none
Knowledge: ok | scaffold (written YYYY-MM-DD on an empty project) → run /generate-knowledge once the code exists | scaffold, project now has content → run /generate-knowledge | missing: [...] → run /generate-knowledge | /generate-knowledge is due ({from} → {to}: ...)

Toolchain: ok | missing tools: [...]
```

## Rules

- Never modify agents, skills, or templates. The only knowledge files you may write are the persistent ones listed in the manifest and `CAPABILITIES.md`.
- Never install, enable or disable a plugin the user did not pick in this run's capability question.
- Never write under the team root. Edit the project's own `.gitignore` only as step 4 describes: the legacy run-state line, replaced by the current one.
- Never run any command other than the manifest lint, `claude plugin list` and the `install` command of a picked plugin, a bash availability check, the run-state migration script and its dry run, the normalizer, the scaffold check, `git -C .claude ls-files`, `git -C .claude status --porcelain --untracked-files=no` and the removals of step 2, `rm -f` of a stale marker, and reading files.
- The files this pass may change, each reported by name: `.git/info/exclude`, the legacy run-state line of the project's `.gitignore`, the run state the migration moves (and the knowledge it rewrites), the first lines the normalizer rewrites, a stale marker, the stale hook entries of `.claude/settings.json`, the persistent knowledge files, `CAPABILITIES.md`, `setup.record`, the old install step 2 removes, and the plugins the user picked.
- Never delete anything in `.claude/` outside step 2's list. An old install that step 2 refused or the developer chose to keep is reported and left alone.
