# Workflow: Review Changes

Read first: `learnings-check.md` (step 2) · `rework.md` (step 5, only for the form of the Verifier vote) · `report-requests.md` (step 6, a request for another form)

The team reviews a finished change from outside and writes a report; it changes no code and writes no file of the repository. The change-reviewer reads the code; you resolve the range, split the work, collect the votes and write the page. Workflow key `review_changes`, context id `review_changes_{slug}_{YYYY-MM-DD}`. The class is final at Step 0: no scope gate, no approval gate. The marker's `phase` names the step just entered; the phase checklist ticks 0 and 1 at step 1 and 7 at step 5 (`change-reviewer: C/H/M/L/N, <recommendation>; Verifier: c of n confirmed`), the others `n/a`.

1. **Resolve the input to one range, and record it.** You do this yourself, since you own the one question. From the developer's words: a pull request number or address, a branch and its base, or "against <ref>"; "the current branch" is `HEAD`. Run only these read-only commands, each logged in `status.md → Operations log` with its exit code and one line of output: `git merge-base`, `git rev-parse`, `git diff --stat`, `git log --oneline <base>..<head>`, `git status --porcelain`, `git branch -r`, `git config --get remote.origin.url` (for the page's links to the repository host); and, when a pull request is named and the `gh` command is installed, `gh pr view --json` for title, description, author, base, head, state, checks and the address; `gh pr diff --name-only`; `gh api` GET of the review threads. Nothing else; never `gh` with a write (`gh api` takes no `-X` other than `GET` and no `-f`, `-F` or `--input`). A first `gh` call that fails for any reason (not installed, not authenticated, a remote on another host) makes `gh` unavailable: logged, no second attempt.
   - **No role contacts the remote, and no git command of yours does.** Both refs must resolve locally: `git rev-parse --verify <ref>^{commit}`, the ref as given or as the remote-tracking branch `git branch -r` lists; with `gh`, the head is the pull request's head commit, which must resolve the same way. When one does not, the run stops here with one line in the task's language, the `Waiting on you:` line, asking the developer to bring that ref into the local repository and then write the next message. No ResearcherExplorer runs and no other command is tried. The marker stays `state=open` at step 1, and the next message continues the run from here.
   - Without `gh`, the pull request fields come from the developer's words and the git range; log which fields were unavailable, and the page names them.
   - When the base is not given and no pull request is named, or a named pull request's head or base cannot be read: one AskUserQuestion, the run's one question. Base candidates: the remote's default branch (the `HEAD ->` line of `git branch -r`) and the release branches it shows; head candidates: the branches it shows; the developer may type either.
   - The range is `<base-sha>..<head-sha>`, where `<base-sha>` is `git merge-base` of the base ref and the head, so the range holds the change's own commits only. Record in `status.md` the line ``**Range:** `<base-sha>..<head-sha>` (<base-ref> ← <head-ref>), N files, +a/−d`` from `git diff --stat <base-sha> <head-sha>`, and in the Decisions log the pull request fields read (number, title, author, state, checks, address) and `Head checked out: yes | no` (`git rev-parse HEAD` against `<head-sha>`). Uncommitted changes are outside the range: when `git status --porcelain` lists any, say so in chat in one line and log it.
2. **Learnings check** (`learnings-check.md`): the matched entries fill the change-reviewer's `prior learnings`.
3. **Size and parts.** From the counts of `**Range:**`. Up to forty changed files and two thousand changed lines (added plus removed): one change-reviewer call over the whole range. Above either: one AskUserQuestion, logged as a gate: "review in parallel parts (recommended) / one pass with a focus: <security | correctness | tests | architecture> / stop here and report only the range".
   - **Parts.** Group the changed paths by top-level directory, then by layer (server side, interface, tests), each part under both limits where possible, together covering every changed path exactly once; give each part's paths as directory prefixes or path patterns git accepts (`git diff --stat=<width>` widens the list when paths are cut short). Name each part in lower case with hyphens, since the name goes into its file name, and log `Parts: <name> (<N> files, +a/−d) · …` in the Decisions log. One change-reviewer call per part, all in one message so they run in parallel, each with the same range, intent and focus and its own paths.
   - **One pass with a focus.** One call over the whole range, the chosen focus as its review focus: it says where the depth goes, never which checklist items apply.
   - **Range only.** No call. Answer in chat with the `**Range:**` line, the commit list and the `git diff --stat` summary, then step 7 with `range only` in place of the recommendation and the counts, and without the fix-run options.

   Each call: handoff → change-reviewer, `mode/phase: review`, model from the cell `review_changes.change-reviewer`; `inputs`: the range `<base-sha>..<head-sha>`, the paths (`all`, or the part's paths), the intent (the pull request title and description verbatim, else the commit messages, else the task in the developer's words), the review focus when the developer gave one, the path `.claude/templates/review-baseline.md`, and the open review threads verbatim with their locations when the pull request has any; `baseline:` names the pre-existing uncommitted files as `none`, so the toolchain runs only on a clean checked-out head; `expected output`: `.dream-team-tracking/{context_id}/reports/review-findings.md` for the whole range, `.dream-team-tracking/{context_id}/reports/review-findings-{part}.md` for a part. Read only the pointer block of a whole-range file until step 6.
4. **Consolidate** (parts only; a whole-range file is numbered already). Read only each part's pointer block, its three leading sections and its `### F-` headings. Two findings at the same `path:line` from two parts are one: keep the higher severity and both explanations. Number the merged list `F-1…` by severity, Critical first, the parts in their logged order within a severity. Write the numbers into the part files by Edit: each heading's `F-<k>` becomes its consolidated `F-<n>`; the lower-severity copy of a duplicate takes the kept one's `F-<n>` and the line `- Merged into: F-<n>` under its heading, and the page shows its explanation under that finding. The counts are the merged list's; the recommendation is the strictest of the parts' (`Request changes` over `Approve with follow-ups` over `Approve`). Log `Consolidated: <total> findings from <p> parts, <d> merged`. From here on a finding's id is its consolidated number: in the Verifier handoff, on the page and in a fix run.
5. **Verify the blocking findings.** One handoff → Verifier, `mode/phase: verify`, model from the cell `review_changes.verifier`, over every Critical and High finding (Medium too when the developer's review focus asks for it); `inputs`: those findings, each verbatim with its id and its `path:line`, `range: <base-sha>..<head-sha>` (the envelope's `baseline:` holds `<base-sha>`), the changed paths, the path `.claude/templates/review-baseline.md`, the path of `.claude/knowledge/REVIEW-CHECKLIST.md`, and the intent in place of a task or plan path; `expected output`: return as final message. With nothing to vote on there is no call, and the Decisions log says `Verifier: not run — no blocking findings`. Record each vote in the findings file that holds the finding, by Edit: one line appended to the finding after its `Confidence:` line, `- verified: yes` for a CONFIRM, `- verified: no — <the Verifier's reason>` for a REJECT. A rejected finding is never dropped and never lowered: it stays at its severity with the disagreement visible, because the Verifier's bar is the bar for sending a Developer to fix something, not for hiding a reviewer's claim from a report. Log `Verifier: <c> of <n> confirmed; rejected: <ids | none>`. Nothing here enters rework.
6. **Report.** Read `.claude/templates/report-html.md` and write its "Review page (Review Changes)" yourself, with Write, in the task's language, to `.dream-team-tracking/{context_id}/reports/review-{slug}.html`, `{slug}` being the run's. You are the consumer of the findings files here: read them in full. They stay the source of truth and are named at the end of the page; the page says nothing they do not, and its header names the pull request fields that were unavailable. Never published: give the path in chat with the counts per severity and the recommendation. A message that asks for another form follows `report-requests.md`.
7. **Close.** `status.md`: first line `[DONE] YYYY-MM-DD — <recommendation>, C<n> H<n> M<n> L<n> N<n>`, `## Result` `ANSWERED`, `Closed` filled; the marker closed with `result=ANSWERED`. Then the closing question (SKILL.md, section Closing) offers, besides the usual options when they apply: **open a fix run for the blocking findings** (the Critical and High findings with `verified: yes`, named by id; present when there is one) / **open a fix run for findings I choose** (present when there is any finding) / **nothing now**. Both fix-run options need `Head checked out: yes`; otherwise drop them and say in one line that a fix run needs the reviewed head checked out, after which the next message may pick findings by number. On "findings I choose" the developer names the ids; when the answer names none, ask once more, the findings listed in the question text as `F-n · severity · path:line`. Log the answer.
   **A fix run.** After this run's marker is closed: Step 0 of a new run, `parent=` this run in the marker and `**Parent:**` in its `status.md`, `## Task` = the chosen findings verbatim, each with its number, provisional class Change Set. It enters `change_set.md` at step 2, the findings standing as its numbered items, with the paths of the findings files under the ResearcherExplorer's `inputs` as the starting point; the scope gate fixes the workflow from the evidence as usual. The findings are not review comments: `review-comments.md` does not run in the fix run, and `change_set.md` step 3 designs every item.

**What you never do here:** write a review brief of your own, read the diff yourself, run a ResearcherExplorer in place of the change-reviewer, run the toolchain, or render the page with a script. An earlier review run did the first, the second and the last, and its report rested on the orchestrator's own reading instead of an independent one; this workflow exists so that it does not happen again. Nor do you check out, stash, move a ref or change a file of the repository: the findings files and the page live in the tracking directory.
