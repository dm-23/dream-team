# Workflow: Review Changes

Read first: `learnings-check.md` (step 2) · `rework.md` (step 5, the form of the Verifier vote) · `report-requests.md` (step 6, a request for another form). Read when step 1 or 3 says so: `merge-review.md`, `re-review.md`, `review-parts.md`; at step 7, `accepted-exceptions.md`.

The team reviews a finished change from outside and writes a report; it changes no code and writes no file of the repository, with one exception: an accepted exception recorded at step 7 is written into the remarks dir, and only when `Head checked out:` is `yes` (`accepted-exceptions.md`). A change that adds files under `<knowledge dir>/proposals/` beside product code is not a knowledge change for that reason: a product change may **add** remarks there, never modify or delete one and never touch any other knowledge path, and the change-reviewer raises "knowledge and product changes in one change" only for those (its Step 3); a merge keeps its own finding (`merge-review.md`). Workflow key `review_changes`, context id `review_changes_{slug}_{YYYY-MM-DD}`. The class is final at Step 0: no scope gate, no approval gate. The marker's `phase` names the step just entered; the phase checklist ticks 0 and 1 at step 1 and 7 at step 5 (`change-reviewer: C/H/M/L/N, <recommendation>; Verifier: c of n confirmed`), the others `n/a`.

1. **Resolve the input to one range, and record it.** You do this yourself. From the developer's words: a pull request number or address, a branch and its base, or "against <ref>"; "the current branch" is `HEAD`. Run only these read-only commands, each logged in `status.md → Operations log` with its exit code and one line of output, never approved one by one (`operations.md` approval is for `TOOLCHAIN.md → Operations` rows only): `git merge-base`, `git rev-parse`, `git diff --stat`, `git diff --shortstat`, `git log --oneline <base>..<head>` (also with `--merges`), `git status --porcelain`, `git branch -r`, `git config --get remote.origin.url` (for the page's host links); and, when a pull request is named and `gh` is installed, `gh pr view --json` for title, description, author, base, head, state, checks and the address; `gh pr diff --name-only`; one `gh api graphql -f query=<a query that reads reviewThreads>` for the threads and their resolved state. Nothing else; never `gh` with a write: no `-X`, no `--input`, no other `-f` or `-F`, and never a query holding `mutation`.
   - **No role reads from or writes to a git remote; the read-only `gh` calls above are the only contact with the host.** Both refs must resolve locally: `git rev-parse --verify <ref>^{commit}`, the ref as given or as the remote-tracking branch `git branch -r` lists; with `gh`, the pull request's base and head commit must resolve the same way. When one does not, the run stops here with one `Waiting on you:` line in the task's language asking the developer to bring that ref into the local repository; no ResearcherExplorer runs, no other command is tried, the marker stays `state=open` at step 1, and the next message continues the run from here.
   - Without `gh` (not installed, or a first call failing: logged, no second attempt), the pull request fields come from the developer's words and the git range; log which fields were unavailable.
   - When the base is not given and no pull request is named, or, without `gh`, a named pull request's head or base is unknown: one AskUserQuestion, the one question of this step. Base candidates: the remote's default branch (the `HEAD ->` line of `git branch -r`) and the release branches it shows; head candidates: the branches it shows; the developer may type either.
   - The range is `<base-sha>..<head-sha>`, where `<base-sha>` is `git merge-base` of the base ref and the head, so the range holds the change's own commits only. Record in `status.md` the line ``**Range:** `<base-sha>..<head-sha>` (<base-ref> ← <head-ref>), N files, +a/−d`` from `git diff --shortstat --ignore-cr-at-eol <base-sha> <head-sha>`, so a file saved with other line endings does not count as rewritten; when `PROJECT-RULES.md` has `## Generated files`, add `-- . ':(exclude)<pattern>'` for each of its patterns and end the line `, generated files excluded`. Record in the Decisions log the pull request fields read (number, title, author, state, checks, address) and `Head checked out: yes | no` (`git rev-parse HEAD` against `<head-sha>`). Uncommitted changes are outside the range: when `git status --porcelain` lists any, say so in chat in one line and log it.
   - **Threads and checks.** Write every review thread read, open and resolved, verbatim to `.dream-team-tracking/{context_id}/research/review-threads.md`: its id, location, state, author and text. From the checks write one line for the handoff: `ci: ok | fail — <the failing checks' names> | pending | unknown`.
   - **Two special changes**, tested before step 2. A merge signal holds (`git log --merges --oneline <base-sha>..<head-sha>` prints a line, or the title, the head branch name or the task says one branch is merged into another) → read `merge-review.md` and follow it. An earlier closed Review Changes run names the same two refs on its `**Range:**` line → read `re-review.md` and follow it.
2. **Learnings check** (`learnings-check.md`): the matched entries fill the change-reviewer's `prior learnings`.
3. **Size and the call.** From the counts of `**Range:**` (of `**Re-review range:**` in a re-review; no limit for a merge). Up to sixty changed files and three thousand changed lines (added plus removed): one change-reviewer call over the whole range. Above either: read `review-parts.md` and ask its question.

   Each call: handoff → change-reviewer, `mode/phase: review`, model from the cell `review_changes.change-reviewer`; `inputs`: the range `<base-sha>..<head-sha>`, the paths (`all`, or the part's paths), the intent (the pull request title and description verbatim, else the commit messages, else the task in the developer's words), the review focus when the developer gave one, the path `.claude/templates/review-baseline.md`, the path of `research/review-threads.md` when it holds a thread (never its text), and the `ci:` line; `baseline:` holds `<base-sha>` and names the pre-existing uncommitted files as `none`, so the toolchain runs only on a clean checked-out head; `expected output`: `.dream-team-tracking/{context_id}/reports/review-findings.md` for the whole range, `review-findings-{part}.md` beside it for a part. Until step 6 read of each file only its pointer block, its leading sections and its `### F-` headings, and in full the findings you put to the vote.
4. **Consolidate** (parts only; a whole-range file is numbered already): `review-parts.md`, which also runs the cross-part pass first.
5. **Verify the blocking findings.** One handoff → Verifier, `mode/phase: verify`, model from the cell `review_changes.verifier`, over every Critical and High finding under `## Findings` (Medium too when the focus is `security`); `inputs`: those findings, each verbatim with its id and its `path:line`, `range: <base-sha>..<head-sha>` (the envelope's `baseline:` holds `<base-sha>`), the changed paths, the path `.claude/templates/review-baseline.md`, the path of `REVIEW-CHECKLIST.md` in the knowledge dir, and the intent in place of a task or plan path; `expected output`: return as final message. With nothing to vote on, no call; the Decisions log says `Verifier: not run — no blocking findings`. Record each vote by Edit in the file holding the finding, one line after its `Confidence:` line: `- verified: yes` for a CONFIRM, `- verified: no — <the Verifier's reason>` for a REJECT. A rejected finding is never dropped and never lowered: it stays at its severity with the disagreement visible. Log `Verifier: <c> of <n> confirmed; rejected: <ids | none>`. Nothing here enters rework.
6. **Report.** Read `.claude/templates/report-html.md` and write its "Review page (Review Changes)" yourself, with Write, in the task's language, to `.dream-team-tracking/{context_id}/reports/review-{slug}.html`, the run's `{slug}`. Here you read the findings files in full; they stay the source of truth, named at the end of the page; the page says nothing they do not, and its header names the pull request fields that were unavailable. Never published: give the path in chat with the counts per severity and the recommendation. The change-reviewer's `Unverified` items are named on the page and in chat, never under `Verify by hand`: the run delivered no change. A message asking for a report gets this page, no second `{topic}.html`; one asking for another form follows `report-requests.md`. A finding with a `Missed:` line whose reason is a missing rule is a lesson about the team: write it as a team-amendment candidate (`amendments.md`), its evidence the finding's line in the findings file.
7. **Close.** `status.md`: first line `[DONE] YYYY-MM-DD — <recommendation>, C<n> H<n> M<n> L<n> N<n>`, `## Result` `ANSWERED`, `Closed` filled; the marker closed with `result=ANSWERED`. Then the closing question (SKILL.md, section Closing) offers, besides the usual options when they apply: **open a fix run for the blocking findings** (the Critical and High findings with `verified: yes`, named by id; present when there is one) / **open a fix run for findings I choose** (present when there is any finding) / **record accepted exceptions — I name the findings** (present when there is any finding; `accepted-exceptions.md`) / **nothing now**. Both fix-run options need `Head checked out: yes`; otherwise drop them and say in one line that a fix run needs the reviewed head checked out, after which the next message may pick findings by number. When "nothing now" is all that is left, no closing question is asked and the final report says so: this workflow's rule, not a Process note. On "findings I choose" or on exceptions the developer names the ids; when the answer names none, ask once more, the findings listed in the question text as `F-n · severity · path:line`. Log the answer.
   **A fix run.** After this run's marker is closed: Step 0 of a new run, `parent=` this run in the marker and `**Parent:**` in its `status.md`, `## Task` = the chosen findings verbatim, each with its number, provisional class Change Set. It enters `change_set.md` at step 2, the findings as its numbered items, the findings files' paths in the ResearcherExplorer's `inputs` as the starting point; the scope gate fixes the workflow from the evidence as usual. The findings are not review comments: `review-comments.md` does not run in the fix run, and `change_set.md` step 3 designs every item.

**What you never do here:** write a review brief of your own, read the diff yourself, run a ResearcherExplorer in place of the change-reviewer, run the toolchain, paste a thread into a handoff, or render the page with a script. Nor do you check out, stash, move a ref or change a file of the repository: the findings files and the page live in the tracking directory, and the one file written outside it is the copy of step 7's accepted-exception entry in the remarks dir, with the head checked out.
