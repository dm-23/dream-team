# Follow-up: a message after a run closed

Read first: `operations.md` (class 4) · `bug_fix.md` (classes 2 and 6) · `review-comments.md` (class 6).

The hook said `<TEAM-MODE-CLOSED>`: the marker names a run whose `status.md` is closed, and the developer wrote into the same session afterwards. Nothing here starts from scratch — the run's diary already holds what was changed, what was verified and what was left to check.

Read the closed run's `status.md`: `## Task`, `## Result`, `## Verify by hand`, `## Decisions log`, and note the paths of its `research/`, `plans/` and `tasks/` files. If the marker lacks `state=closed`, rewrite it to the closed form now (SKILL.md → "Sticky team mode"), with `result=` from `## Result` and `verify_open=` counted from `## Verify by hand`.

Classify the message into one of six classes. Ask one AskUserQuestion naming the two candidate classes only when the words fit two of them; otherwise decide, and say the class in your first line.

1. **Verification result** — the developer reports an outcome without a defect: "checked, works", "committed", "deployed to prod", a sha. Append ` — confirmed YYYY-MM-DD` to each `## Verify by hand` line the message covers; set the status word of `## Result` to the strongest the evidence allows (`COMMITTED <sha>`, `DEPLOYED <environment>`, `VERIFIED` only when no line is left unconfirmed); log the message in `## Decisions log`; rewrite the marker's `result=` and `verify_open=`. When the word becomes `VERIFIED`, delete the marker (`rm -f`, then `ls -a`). Reply in one line. No run opens.
2. **Defect in the delivered change** — a symptom of broken behaviour in what the run changed: "still broken after the deploy", "the modal reloads again". A comment on the code or its design is class 6, not this. Open a linked Bug Fix run: Step 0 as usual, `parent={closed context_id}` in the marker and `**Parent:**` in `status.md`, `## Task` = the message verbatim. Skip `bug_fix.md` step 1 when the message carries a symptom. Instead of steps 3–4: handoff → Reviewer `mode: diagnose`, model from the cell `bug_fix.reviewer:diagnose`; `inputs`: the parent's `status.md` path, its `## Result` line, its baseline sha, the paths of its task files or plan and of its `research/exploration.md`, and the symptom in the user's words; `expected output`: `.dream-team-tracking/{context_id}/research/diagnosis.md`. Read only its pointer block. `Defect: in the delivered change` together with `Fix inside parent files: yes` → `bug_fix.md` step 5 (the gate quotes `Cause:` and `Proposed fix:`), then steps 6–9. Anything else → handoff → ResearcherExplorer `mode: targeted` with the parent's `research/exploration.md` path and `research/diagnosis.md` under `inputs` as the starting point, then `bug_fix.md` steps 4–9. Record the class and the diagnosis verdict in `## Decisions log`.
3. **New scope** — "now also add …", a different task in the same area. Step 0 of a new run as usual; `parent=` in the marker and `**Parent:**` in `status.md` record the lineage for the diary. The new marker replaces the closed one.
4. **Operations** — "deploy it", "roll back", a reading from a running system: `operations.md`, logged in the closed run's `## Operations log`; a deploy row that exits 0 sets `## Result` and the marker's `result=` to `DEPLOYED <environment>`. The run stays closed.
5. **Not about the run** — no relation to the task, the files or the verification: say so in one line, answer as a standalone request, leave the marker as it is.
6. **Review comment** — a reviewer's comment on the pull request, or the developer's complaint about the delivered code or design: "over-engineered", "why a poller", "this is not what the reviewer asked for". Open a linked Bug Fix run as in class 2, with `## Task` = the message verbatim, and run `review-comments.md` in place of `bug_fix.md` steps 3–4. A code item goes to `bug_fix.md` step 5 when its diagnosis says `Defect: in the delivered change` and `Fix inside parent files: yes`. Otherwise it first takes class 2's ResearcherExplorer route and `bug_fix.md` step 4. Every item meets the one gate of `review-comments.md` step 5. With no code item, the run closes `ANSWERED` as that file says.

In classes 1, 4 and 5 the run stays closed and the marker stays `state=closed`. A message that mixes classes — "deployed, but the export is still empty" — is handled in order: the verification first (class 1 or 4), then the defect (class 2 or 6).
