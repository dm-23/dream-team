# Learnings check (every workflow except Docs, before any Brainstorm or research)

Read `LEARNINGS.md`. In the current shape it is an index and nothing else, so read it whole. **If it still carries `## [` entry bodies below the index, this deployment has not been migrated yet**: read only from `## Index` down to the first `## [` line, stop there, and offer the refresh as `knowledge-refresh.md` says (its shape work moves the entries into their own files) — reading an un-migrated log whole is the cost this shape exists to remove, and the team layer updates before the knowledge layer does. Match rows whose title or tags overlap the task terms, then open the matched entries: from `learnings/` once they live there, otherwise from the entry bodies further down the same file. An entry's file is `<operative dir>/learnings/YYYY-MM-DD-{slug}.md`, with `{slug}` derived from the row's title by the rules in `templates/learnings-entry.md` (not the run slug), including the `-2`, `-3` suffixes. Put their title + "Fix pattern" lines into every handoff's `prior learnings` field, and record matched titles in status.md. The `team amendments` field beside it is filled from the collector, as `amendments.md` → "Active" says, not from the inbox.

Then count the index rows, and in Bash run `grep -rhE '^[[:space:]]*(- )?\[(PROMOTE|STALE-CHECK)\]' <operative dir>/learnings/ | wc -l` (and look through any entry bodies still inline); the resolved forms carry `RESOLVED` inside the brackets and do not count. Bash, not the Grep tool: the operative dir is git-ignored and the Grep tool skips ignored paths, so it would report an empty inbox that is not empty. If the rows exceed `knowledge.budgets.learningsIndexMaxRows` or any mark is pending, and status.md → "Process notes" carries no `Inbox due:` line yet (the hook's notice at Step 0 normally put one there), write `Inbox due: offered YYYY-MM-DD — deferred to close ({N} pending marks, {R} index rows, budget {M})`: the marker is already `state=open` here, so the generator cannot run now, and the closing question offers the refresh instead (`knowledge-refresh.md`). A resumed session that finds an `Inbox due:` line says nothing more about it. The hook injects the same notice as `<TEAM-INBOX-DUE>` on the prompt that starts a run; it is the same offer, not a second one. Never block the run on it.
