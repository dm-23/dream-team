# Workflow: Quick Fix

Read first: `learnings-check.md` (step 2) · `scope-gate.md` (step 2) · `rework.md` (step 7) · `operations.md` (close)

The minimum change first, and every add-on a separate decision of the user. Quick Fix has no size cap of its own: a Quick Fix the user named continues above 3 files or with wiring when the user says so at the scope-gate question.

1. Clarify only if ambiguous (≤3 questions).
2. Learnings check. Handoff → ResearcherExplorer (`mode: targeted`, `expected output`: `research/exploration.md`), as Bug Fix step 3: `Test one` and `Build` under `constraints` when they apply. Workflow fix (`scope-gate.md`), from its pointer block — you do not read the report. A run that arrived here from the choice in `scope-gate.md` has this step done; continue at step 3.
3. **Approach consult.** Handoff → Advisor, `mode/phase: approach`; `inputs`: the task text, the exploration **path** and the learnings lines, never the exploration text; `constraints`: `task shape: list of N items | single concern`, set by you from the task (a list of independent items → list), and every later `approach` consult of the run carries the same `constraints`, `task shape` included; `expected output`: return as final message. On `INSUFFICIENT EVIDENCE`: one handoff → ResearcherExplorer, `mode: targeted`, `inputs`: the Advisor's `To advise I need:` lines, `expected output`: `## Answers to open facts` appended to `research/exploration.md` (the evidence route of `quorum.md`); then the same consult again with that section named under `inputs`. When that pass's pointer block says `Decision marks: N` with N > 0, the resend names the section and the Advisor resolves its `decision` entries under `Resolved:`; you never pick between the options. At most one such resolution per run; a later `decision` mark goes to the user via AskUserQuestion with the entry's options. At most two evidence routes per run; a third `INSUFFICIENT EVIDENCE` goes to the user via AskUserQuestion with the Advisor's list.
   **Budget.** At most four counted Advisor calls per run, each logged in status.md → "Decisions log" as `advisor: {mode} #{n}`; `INSUFFICIENT EVIDENCE` and its resend are not counted. Phase 3 line: `advisor: {N consults, M evidence routes}`. On reaching four, write `advisor budget reached` to "Process notes" and the final report; from then on a consult the budget no longer allows (a keep as worded, an approach-changing edit, a blocked return) goes to the user via AskUserQuestion instead, a blocked return with the Developer's report summarised. Never present the packet as the Advisor's: it is the team's synthesis.
4. **Gate**, via AskUserQuestion, built from the packet; its shape follows `task shape`.
   - **Single concern.** Question 1: "Minimum: {change}; files: {list}; test: {yes — reason | no — reason}", options approve / edit / reject. On `Verdict: Reframe` question 1 leads with the reframe in the Advisor's words, "As worded the task asks X; the evidence says the problem is Y", and shows the Minimum for the reframed problem; options approve the reframed minimum / keep as worded / reject. "Keep as worded" runs one more counted `approach` consult, its `constraints` step 3's plus `as worded, no reframe`, then the gate again. Questions 2–4, one per add-on: "{title} — files: {list}; why it is not in the minimum: {reason}", options take now / later / drop. An add-on whose files are outside the exploration's file list (the pointer block's `Files:` line), or that adds wiring the exploration did not list (`Wiring/surface:`), is offered only later / drop, and its question says why. The packet's `Also noticed:` lines are copied to the final report under "Also noticed", no question asked.
   - **List shape.** Question 1 as above. Items outside the exploration's files or wiring, as above, are set aside first: recorded `later`, named in question 2's text with why, asked at close. Question 2 covers the remaining items. Two or more: one multi-select in the Advisor's order, a selected item `taken`, an unselected one `later`; it carries four options at most, and items past the fourth are recorded `later`, named in the question text and asked at close; dropping an item from the multi-select happens only through "edit". One: the single-concern add-on question, take now / later / drop. None: only question 1.
   - **Record** in "Decisions log": the approved Minimum bullets and one line per add-on, `add-on: {title} — taken | later | dropped`; phase 4 line: `minimum approved, add-ons: T taken / L later / D dropped`. On edit: apply the user's words; an edit that changes the approach rather than the wording runs one more counted `approach` consult with step 3's `constraints`, then the gate again, as after "keep as worded". The Developer only ever gets a Minimum the user approved at a gate.
5. **Implementation.** The `constraints` of the Tester, Developer and Reviewer handoffs carry `reports a bug: yes | no` (yes when the task reports something broken). When the approved change needs a test — the user asked, `PROJECT-RULES.md` requires one, an existing test pins the changed behaviour, or the gate approved `test: yes` — a task that reports a bug runs the Tester first, as `bug_fix.md` step 6 (the `pass` question included); otherwise the Developer runs first and the Tester after, as `small_change.md` step 5. The Tester's model cell is `quick_fix.tester`. Record `Tests (Tester: run)` or `skipped — reason` in status.md either way. Handoff → Developer: the inline task is the approved Minimum bullets plus the taken add-ons, with the exploration **path**. A Developer return of `Plan conflicts with convention:`, or a report that it could not complete the task → one counted handoff → Advisor, `mode/phase: blocked`, `inputs`: the Developer's report verbatim and the exploration path; then the Developer again with the Advisor's direction. A second such return goes to the user. `INSUFFICIENT EVIDENCE` from this consult takes the route of step 3 for the facts only: not counted against the Advisor budget, counted toward the two evidence routes; a `Decision marks: N` with N > 0 from that pass goes to the user via AskUserQuestion with the entry's options, never to the Advisor.
6. **Review.** Handoff → Reviewer (single pass, baseline attached); `inputs`: the approved Minimum bullets and the taken add-ons (for the `Criteria:` line), the Tester's block or the `skipped — reason` line (for `Fail-before:` when `reports a bug: yes`), and on a rework pass every waived or edited criterion line verbatim. No Advisor consult on a diff: the Reviewer is the second checkpoint.
7. Rework: `.claude/skills/team/references/rework.md`; the Verifier's cell is `quick_fix.verifier`.
8. **Report; close; closing question.** The deferred items are the add-ons whose last `add-on:` line in the Decisions log says `— later` (the last line per title wins), re-read from status.md in that turn — never from memory; a resumed run has nothing else. The final report carries a "Deferred add-ons" section (those items) and an "Also noticed" section. Close status.md and the marker. Then one AskUserQuestion: question 1 is the closing question of SKILL.md, section Closing; questions 2–4 are built from the deferred items. One question per item, "{title}", options open now as a linked Small Change / later (kept in the report) / drop. With more than three items, questions 2 and 3 are two multi-selects over the same items, "open now" and "drop"; an item in neither stays `later`. A multi-select carries four options at most: items past the fourth stay `later`, are named in the question text and stay in the report. With none, only question 1. "Open now": after this run's marker is closed, Step 0 of a new run with `parent=` this run, `## Task` = the add-on line, provisional class Small Change; several run one after another, never in parallel, each with its own gate, and you say the order. "Later": the line stays in the report and the Decisions log; the developer starts it with `/team` by hand. Log each answer: `add-on: {title} — opened as {context_id} | kept | dropped`.
