# Committed mode: the refresh

Read by the Knowledge Generator in committed mode when the first argument is `refresh` ("What this run does" in `SKILL.md`). The refresh is the one run that writes committed knowledge. It runs in place on the checked-out release branch, moves onto a work branch of its own, regenerates what the code has moved past, turns the remarks waiting under `proposals/` into rules and facts, and leaves one commit that touches only the knowledge dir. `knowledge.refresh` does the git part; this file is the rest. Every path is project-root-relative; `<knowledge dir>` is the resolver's `project`. `<stamp>` is `YYYY-MM-DD-HHmm`, taken once, and `<work>` is `.dream-team-tracking/knowledge-backup-<stamp>/work/`, where every source this run hands a tool is written with Write.

The refresh takes no file names: a name after `refresh` is refused in one line, `The refresh decides its own work list; run /generate-knowledge refresh alone.` While the directory `tracking.legacyDir` exists, it is refused with `run state is still in the legacy directory — run /team-setup first`. Product changes in the working copy stay where they are and are never committed; nothing here stages, restores or edits a path outside the knowledge dir.

1. **Begin.** `bash .claude/{knowledge.refresh} begin`. Exit 1 or 2 → report its message verbatim and stop: nothing has changed. Exit 0 → report its three lines verbatim. From here until step 8 the run is on the work branch.

2. **The branch line.** `same` or `new` → no question here (`new` means there is no baseline yet, which step 3 handles as the drift state `missing`). `<old> → <new>` → one question, with AskUserQuestion, in the language of the request: `The baseline was taken on <old>; this refresh runs on <new>.` Options: **<new> was cut from <old>** (continue from the baseline: the drift report decides), **a merge brought <old>'s knowledge in** (every located topic is regenerated, since the knowledge no longer matches one branch's code). `Consent: given` takes the second.

3. **The work list,** built in this order, each item adding files; nothing is written yet.
   1. **Missing `Covers:` lines.** Every generated file and topic (every `*.md` under the knowledge dir outside `rules/` and `proposals/`) with no `Covers:` line within its first five lines gets one, as "Covers" in `SKILL.md` says, written from the paths the file itself names; its text is left untouched. Look for them yourself: the first refresh after the migration finds none anywhere, and the shape check cannot report them while there is no `BASELINE`.
   2. **Drift.** `bash .claude/{knowledge.drift} --list`. State `listed` → its `marked` files. `over` or `unresolved` → every located topic (a file or topic whose `Covers:` line lists patterns). `scaffold` → every file; on a project still empty (`checks.knowledgeScaffold` prints `project: empty`) nothing can be derived: report it and run `abort` (step 6). `missing` → the question of step 6 offers **regenerate every located topic** and **the knowledge was generated at this commit: write only the `Covers:` lines and the baseline**; `Consent: given` takes the first. `clean` → nothing from this item. The branch question of step 2, answered with a merge, makes it every located topic whatever the state.
   3. **Knowledge changed outside a refresh.** `<K>` is `git log -1 --format=%H -- <knowledge dir>/BASELINE`; when it prints a commit, every generated file `git diff --name-only <K> HEAD -- <knowledge dir>` lists outside `rules/` and `proposals/` (a merge brought it in, unverified).
   4. **Uncovered code.** Each `uncovered` record → a new topic in the file whose subject it is, or a wider `Covers:` on an existing topic that already describes it; say which.
   5. **Dead patterns.** Every file `checks.knowledgeShape`, run as `checks.knowledgeShapeRunFrom` spells out, reports for a pattern that matches nothing or has a backslash → its `Covers:` line is rewritten as in item 1.
   6. **Conventions.** The drift report never marks a file whose `Covers:` is `conventions`: run "Staleness" on those, and every one with a `STALE` line joins the list.
   7. **Authored lines.** When the shape check lists an authored line, or `REVIEW-CHECKLIST.md` has an `## Accepted exceptions` entry other than `- none`, the extraction of "Authored rules" is due, before any other write.
   8. **Shape.** A file outside the list that the shape gate of "Shape work" finds out of shape or over budget → its move or rewrite. No other run can fix it once the knowledge is committed.

4. **Authored rules** are re-verified as "Authored rules" says; each `RULE UNBORNE` is removed on consent.

5. **Remarks.** Every file under `<knowledge dir>/proposals/` (in the project: read it with Read), and every entry of this developer's own inbox that carries no `[SUBMITTED` line, plus the lines of its `review-exceptions.md` without the ` [SUBMITTED]` suffix (through `inbox.sh` only), are triaged with the classes of step 2 of "Triage the learnings inbox (private mode)", verified against the code on this branch. Remarks that say the same thing are merged into one outcome.
   - A confirmed `rule`, or an exception (`[EXCEPTION] <line>` in a proposal, or a line of the developer's own `review-exceptions.md`) whose cited line is still in the file it names (`grep -F`) → a rule file, as step 5 of that triage writes one, with `Source: proposal <file name>` for a proposal and the source that step gives for the developer's own entries; `Exception:` is the line without its `- `. Never a second rule file with the same path, cited line and rule.
   - A confirmed `fact` → the file it names joins the work list, and the regeneration reflects it; a `[STALE-CHECK]` it carries counts as resolved by that.
   - A remark the code contradicts, one the knowledge or a rule already holds, an exception whose cited line is gone, and a `summary`, `team` or `obsolete` remark → rejected, with its reason.
   - A `trap` that is not yet a rule → kept: it stays in `proposals/`, or in the developer's inbox. A remark whose evidence is not on this branch (its path, line or sequence exists only elsewhere) → kept, untouched.

   Nothing is written in this step; step 7 applies it. Every consumed or rejected file under `proposals/` is deleted there, and gets one line for the commit body, naming the file as it stands in `proposals/`, which is how `knowledge.proposals status` finds the reason later: `consumed: <file> → rule:<slug>` or `consumed: <file> → <knowledge file>`, or `rejected: <file> — <reason>`. A consumed or rejected entry of the developer's own inbox gets the same line with its inbox name, and is removed with `inbox.sh remove` only after `finish` exits 0 (step 8; a consumed exception line: the file rewritten without it, through `inbox.sh put review-exceptions.md`), so a refresh that is never committed leaves the developer's inbox as it was.

6. **One question,** with AskUserQuestion, in the language of the request, listing all of it, only what has members: `N files to regenerate: <names>`, `C Covers lines to write`, `S files to restructure: <moves and rewrites, the extraction>`, `P remarks: A consumed, B rejected, D kept`, `U rules not borne out`, the `missing` choice of step 3 when it is due, and `backup of the inbox to .dream-team-tracking/knowledge-backup-<stamp>/operative/` when step 5 removes or rewrites an inbox entry (taken once the refresh is committed, step 8). An empty list still moves the baseline: say `nothing to regenerate; the baseline moves to <short sha>`. Options: **Do it** (everything listed; while the `missing` choice is due, two options in its place, one per choice of step 3) and **Nothing**, which runs `bash .claude/{knowledge.refresh} abort` and reports its output verbatim; abort puts the knowledge dir back and the run ends. `Consent: given` skips the question and does everything listed.

7. **Apply,** on the work branch:
   - The knowledge dir is not backed up: `git` is the way back. `begin` refused any change under it, so the base commit holds exactly the knowledge as it was. Before the first write, copy that tree out of git, without touching the index or the working tree, for the integrity check below: `mkdir -p .dream-team-tracking/knowledge-backup-<stamp>/base`, then, from the project root, `git archive <base> -- <knowledge dir> | tar -x -C .dream-team-tracking/knowledge-backup-<stamp>/base`, `<base>` being the short sha `begin` printed. The archive's paths are relative to the project root, so the copy lands at `.dream-team-tracking/knowledge-backup-<stamp>/base/<knowledge dir>`; call that `<base copy>`. Never `git checkout` or `git restore` into another directory: both rewrite index entries. The copy is read by the check only and never written.
   - The extraction first, its output reported verbatim (`bash .claude/{knowledge.ruleExtractor} <knowledge dir>`), then the moves and rewrites of "Shape work".
   - Then the integrity check, before anything else is written: `checks.knowledgeIntegrity` run as `checks.knowledgeIntegrityRunFrom` spells out, with `<base copy>` as the backup side and the knowledge dir as the other (`bash .claude/checks/verify-knowledge-integrity.sh <base copy> <knowledge dir>`). Report its output verbatim. A failure means this run broke its own contract: say that, write nothing more, and ask one question, with AskUserQuestion: **Abort** (`bash .claude/{knowledge.refresh} abort`, its output reported verbatim; the knowledge dir is back at base) or **Leave it on the work branch** (for the lead to inspect; `finish` or `abort` later). `Consent: given` takes **Abort**.
   - Then the `Covers:` lines, the rule files of step 5, the removal of the rules not borne out and of the consumed and rejected proposals. Nothing in the developer's own inbox is removed or rewritten here (step 8).
   - Then the files of the list, regenerated as step 5 of "Process" regenerates a generation list, from this branch's code. Run the `TOOLCHAIN.md` commands for its `Verified` column as "TOOLCHAIN.md" says; cross-check as step 7 of "Process" says; print the size table.
   - Never write `BASELINE`: `finish` writes it. Never commit, stage, switch branch or reset yourself.

8. **Finish.** Write the body lines of step 5, one per line, to `<work>/refresh-body.txt`, then `bash .claude/{knowledge.refresh} finish --message-file <work>/refresh-body.txt`.
   - Exit 0 → report its `warning:` lines and its three last lines verbatim. A `warning:` names a path outside the knowledge dir that changed during the refresh, a build or a test included; it is not in the commit, and it stays as it is. Only now the developer's own inbox changes, when step 5 consumed or rejected any of its entries: first `inbox.sh backup .dream-team-tracking/knowledge-backup-<stamp>/operative`, its path named in the report; then `inbox.sh remove` of those entries, and, for exception lines, the whole new `review-exceptions.md` (its first line kept, every other line byte for byte) written with Write to `<work>/review-exceptions.md` and `inbox.sh put review-exceptions.md <work>/review-exceptions.md`; every read and removal of the developer's own entries goes through `inbox.sh`. Any `finish` that does not exit 0 leaves the inbox untouched.
   - Exit 1 with check lines (the shape or the neutral check) → fix in the knowledge dir what each line names and run `finish` again, at most twice more; still refused → report its lines and stop, saying the refresh is kept on the work branch for `finish` or `abort`.
   - Exit 1 naming commits on the work branch → someone committed there. Report the commits it names and stop. Never reset, never abort over them: the lead decides.
   - Exit 2 because a commit hook rejected the commit → the refresh stays on the work branch with its state kept. Report the hook's message verbatim. A cause inside the knowledge dir is fixed there and `finish` runs again, at most twice more; still rejected, or a cause elsewhere, which this run never edits → report it and stop, naming `finish` (after the fix) and `abort` as the two ways on.
   - Any other exit 1 (no state file, not on the work branch) or exit 2 → report its message verbatim and stop.

**Never** push, never open a pull request, never merge. The `push:` and `pull request:` lines are the lead's to run.

**Report:** the three lines of `begin`, the work list as done, the extraction's line, the integrity check's output, the rejected remarks with their reasons, the kept ones and why, the rules not borne out that were removed, unverified commands, the size table, and `finish`'s warnings and three lines verbatim.
